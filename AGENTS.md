# AGENTS.md — памятка для ассистентов

## Что это за проект

Автоматизатор создания персонажа для WoW: Forever (Classic+, клиент 1.60.1).
Python-приложение с GUI (tkinter): эмулирует клики/клавиатуру в окне игры
(pyautogui), определяет состояние экрана по пикселям (PIL/ImageGrab),
собирается в один `.exe` через PyInstaller.

## Структура

- `wow_char_auto.py` — всё приложение (GUI + логика бота + справочники).
  Ключевые разделы:
  - `CLASSES`, `RACES` — проверенные на живом клиенте таблицы «раса → классы»
    и «раса/пол → список слайдеров внешности» + `ystart` первого слайдера.
  - `POS` — все координаты как **доли (fx, fy) от клиентской области окна**
    игры. Калиброваны на 2560×1440; в коде есть масштабирование под размер.
  - `Bot` — движок: `classify()` (детект экрана по контрольным пикселям,
    авто-закрытие Esc-меню и окна «ОК»), `do_full_flow()` (полный сценарий),
    `run_simple()` (упрощённый режим), `run_relog_test()` (3 релога через
    30 секунд без «Завершить»), `run()` (цикл попыток + релог).
  - `App` — GUI на tkinter; поля кастомизации спрятаны в `custom_frame`,
    отдельная кнопка `start_relog_test()` запускает тест релога.
- `build.bat` — пересборка exe (`pyinstaller --onefile --windowed`).
- `.github/workflows/build-release.yml` — Windows-сборка и smoke-тест для PR
  в `release`; после push в `release` публикует GitHub Release с exe.
- `dist/WoWCharAuto.exe` — сборка (в git не входит).
- `survey_*_panel.png` — эталонные скрины панелей внешности (в git не входят,
  **содержат личные данные аккаунта — не коммитить**).

## Сборка и запуск

- Зависимости: `pip install pyautogui pygetwindow pillow pyinstaller`.
- Сборка: `pyinstaller --onefile --windowed --name "WoWCharAuto" wow_char_auto.py`
  (или `build.bat`). Проверка: запустить `dist\WoWCharAuto.exe`, в диспетчере
  задач появится процесс, GUI стартует с дисклеймером.
- Полноценный тест кликов возможен только на машине с запущенным клиентом
  игры, дошедшим до экрана создания персонажа.

## Критично понимать

- **Все координаты — доли от клиентской области** (`GetClientRect` +
  `ClientToScreen`), НЕ от окна и НЕ абсолютные пиксели. Расовые портреты,
  кнопки и слайдеры имеют дробные координаты в `POS`/`RACES`.
- **UI-масштаб игры у пользователей может отличаться** — раскладка нижней
  панели (иконки классов ~fy 0.87–0.93) плавает. Это известный источник багов
  (см. открытую проблему: выбор класса при нестандартном UI scale).
- Детектор окна «ОК» (ошибка фракции): трёхступенчатый — форма красной
  полосы + тёмный фон вокруг + ярко-жёлтый текст над кнопкой. Красная одежда
  моделей нежити/орка обязана давать False (проверено на эталонах).
- Проверка выбора расы: длина верхней яркой рамки портрета (≥60 px).
  Детектор принимает золотой и почти белый оттенки, проверяет пять строк
  вокруг кромки. Проверен офлайн на выбранных дворфе, нежити и тролле;
  невыбранные портреты на тех же скриншотах дают False. Если рамка не
  распознана, но диалога недоступности фракции не было, сценарий продолжает
  к выбору класса; при обнаруженном диалоге попытка завершается ошибкой.
- Все параметры внешности — абсолютные номера: бот сбрасывает каждый к 1
  двенадцатью кликами левой стрелки, затем делает `N-1` кликов вправо.
  Имена вводятся посимвольно через `SendInput` с `KEYEVENTF_UNICODE`,
  без буфера обмена и зависимости от раскладки. Перед вводом каждое из двух
  полей очищается: `End`, затем 24 нажатия `Backspace` (без `Ctrl+A`).
- Доступность имени определяется по области `POS["name_status"]`: зелёная
  галка разрешает «Завершить», красный крест останавливает создание, неизвестный
  статус логируется и не блокирует сценарий. Проверка есть в полном, упрощённом
  и тестовом режимах; результат всегда пишется в журнал.
- Релог при `has_other_server_chars=True`: выход «Назад» из кастомизации →
  выбор расы (1 сек) → список PvP (5 сек) → переподключение (10 сек); после
  Enter ждёт 20 сек, открывает «Свод правил», через 5 сек выбирает PvP →
  «Выбрать» и ждёт 30 сек. Затем принимает select либо нажимает `new_character`
  в списке персонажей, ждёт 2 сек и требует select. Координаты — `back`,
  `charlist_back`, `charlist_rules`, `new_character`, `realm_pvp`, `realm_choose`
  в `POS`. Детектор charlist требует сигнал в `probe_newchar` и красную кнопку
  в `new_character`, чтобы красная одежда модели не имитировала reconnect.
  При выключенном флажке используется прежний короткий релог через Esc.
  Тёмно-красная кнопка
  переподключения (например, пиксель 97,2,1) распознаётся отдельным порогом;
  общий `is_red()` не ослаблять. Для любого варианта reconnect дополнительно
  требуется тёмный `probe_right`: это отсекает кастомизацию с красной кнопкой
  «Завершить» и тёплым цветом в центре экрана.
- Тест релога никогда не должен создавать персонажа. `click()` блокирует
  `POS["finish"]`, а `press()` разрешает Enter только после повторной
  классификации экрана как reconnect/select. После каждой успешной настройки
  `run_relog_test()` выводит сообщение и подаёт звуковой сигнал, затем продолжает
  оставшиеся релоги; `attempt_create()` в тесте не вызывается.
- Проверка кода без игры: детекторы можно гонять офлайн на эталонных скринах
  (monkeypatch `ImageGrab.grab` и `pyautogui.click`), как делалось для
  окна «ОК».
- Настройки/логи/debug-скрины пишутся рядом с exe (`wow_char_auto_settings.json`
  содержит имена персонажей — не коммитить; `.gitignore` это закрывает).

## Правила репозитория

- В git только: `.gitignore`, `README.md`, `build.bat`, `wow_char_auto.py`,
  `.github/workflows/build-release.yml`.
- `dev` — ветка разработки: вся текущая работа и коммиты ведутся в ней.
- `main` — основной код: MR/PR в неё создаются **только из `dev`**.
- `release` — билды и релизы: MR/PR в неё создаются **только из `main`**;
  PR должен пройти обязательную проверку GitHub Actions `build`; push в неё
  запускает публикацию релиза.
- Не запускать `git push` без явной просьбы пользователя.

## Версионирование

- Текущая версия хранится в `APP_VERSION` в `wow_char_auto.py`, формат `0.0.0`.
- Первое число — основная версия: `0` — ранний доступ, `1` — релиз.
- Второе число — мажорная версия: увеличивается при новых функциях и
  существенных изменениях.
- Третье число — минорная версия: увеличивается при фиксах и исправлениях
  в рамках текущей мажорной версии.
- Перед MR/PR из `main` в `release` версию необходимо увеличить. GitHub Release
  и его тег используют номер из `APP_VERSION` (`v0.0.0`).
